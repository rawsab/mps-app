# 0030 — Daily nutrition entry and coach notifications

Date: 2026-11-17 · Status: implemented, manual UI verification pending

- FR-03/09: client Nutrition opens the current program directly, with **Today’s daily entry** first. It asks for today's weight in pounds, yesterday's calories consumed and yesterday's caloric output. A single Save daily entry action saves the changed fields atomically through the same protected spreadsheet write path. Other programs remain accessible below the current program.
- Each field has an empty circle until its value matches an acknowledged saved record, then a green circle-and-tick and Saved label. All three fields are required for the form's complete-for-today state; actual zero calories are accepted, while blank is missing. The overall section uses the existing success token, a green completion circle and a completion badge. Saved fields stay editable for corrections.
- The top form appears on active client program pages as well. Program baselines, stats and editable weekly spreadsheets remain below it. Form, spreadsheet, Home and Progress use the same client/date actuals. Changes made in one refresh the others. Unsaved values stay through failures and navigation is guarded. An in-progress entry keeps its original day if the server date changes at midnight, rather than relabelling it as a new day's entry.
- A confirmed save remains acknowledged locally if the follow-up refresh loses its connection. A failed background refresh retains the last loaded program and form instead of unmounting them. Retrying a failed write reuses its request IDs; stale records require reloading before overwrite.
- Migration `20261117000026_nutrition_activity.sql` adds a protected daily activity record and per-staff seen state. A trigger on existing attributed entry history creates or updates **one notification per client / weigh-in day**, mapping calorie activity dates to the next displayed weigh-in day. Both the top form and spreadsheet edits use it. Overlapping programs share the same notification and daily data.
- Only meaningful client changes notify. Lost-response retries, identical-value saves, empty calorie records, coach-only entries and coach corrections do not create or revive an alert. Failed batches roll back alerts with their data. Later client changes make the same daily item unread again. Existing historical entries are not backfilled into new notifications.
- Reviews, To review, the unread badge, Recent updates and client activity history combine training and nutrition. Nutrition items retain client profile pictures, show partial/complete status and available weight/calorie values, and open the matching published spreadsheet day. Returning from that sheet respects the originating Reviews or client page. Rows remain visible after coach corrections with attribution; corrections do not change the client's notification time.
- Read state remains per staff member. Opening a nutrition item marks it read; Mark all as read covers both services. Coach feeds, latest unread items and recent updates poll once a minute. No email or push notifications are introduced.
- Verification: typecheck, 269 unit tests and build pass; 78 targeted database assertions (37 nutrition activity, 26 existing Reviews, 15 existing client activity); 6 nutrition/combined-feed HTTP checks. Local migration applied without a reset. Existing bundle-size warning remains. No browser automation or screenshots. No command was skipped awaiting approval during this increment.
